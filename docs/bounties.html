Launch Claim Checker: money behind a launch claim

← Back to the free checker

The checker says what two pages show. A bounty puts money behind it: test GEN held by the contract that pays the first person who shows, on the explorer pages the poster pinned, that a launch claim is false.

  1. Post. Anyone locks a pot behind one claim about one coin and pins the pages: a block page address with {n} for the block number, and/or one mining page. Hunters never supply an address.
  2. File. A hunter files a sealed claim: only a fingerprint (a sha256 of the bounty's number, the hunter's address, the rule, the block number and a secret salt) goes on the chain, so a filing does not show which block it is about. Filing costs 2% of the pot, at least 0.001 GEN, which is burned. The time the filing was sent fixes its place in the queue, and it can be judged for 30 minutes.
  3. Judge. Only the filer can open the claim, by revealing the rule, the block and the salt. Validators then read the pinned page. Each one's model fills in a short form and plain code checks every value against that validator's own copy of the page. They must agree on the amount exactly, or on the top miner by name.
  4. Pay. A filing that pays wins the whole pot as soon as no filing sent before it is still waiting to be judged. A copy made after a reveal is filed later, so it ranks behind. With no winner, the poster takes the pot back 60 minutes after the expiry.

    The rules, read from the contract

    Limits

    • Rule P1 is a model's reading with code checks, not a proof. It covers blocks 0 to 100 and the first 6,000 characters of a page. A coin with a disclosed developer fee in its early blocks pays out under it.
    • For the mining rule the hunter picks the moment, and pool names are written by miners. The more blocks a bounty asks for, the less luck can decide it. Rows with a word such as "unknown", "others" or "burn", and rows with the all-zero or 0x…dead address, are refused. It is a filter, not a guarantee, in both directions: an unusual label can pass, and a real name that contains a listed word is refused.
    • A reveal is public from the moment it is sent. If the judgement then does not pay (validators do not agree, a reading finds nothing, three judgements end with the page unreadable, the wrong page or a model answer out of form, or the 30 minutes run out), someone else can file the same claim. Reveal once the filing shows in the list, and early enough to try again.
    • Amounts and block counts must be printed with a dot for decimals and commas, or nothing, between thousands. A number that could be one group of a longer number written with spaces is refused as ambiguous: "2" in "2 000 000"; "500.00" right after another short number, as in "1 500.00", also when that "1" is an output index or a rank; a number of up to three digits right before a three-digit column, as in "840 512 MH/s"; an amount with exactly three decimals right before another number. A true allocation or count printed that way cannot be claimed.
    • Under the mining rule there is only one possible claim, so a seal hides nothing there: a filing made blind and kept live outranks a later hunter whose reveal shows that the page now pays.
    • Both rules are a model's reading with code checks. Which amount on a block page is the extra allocation, and which row of a mining page is the top miner, are the model's choices; code checks that every value is printed on the validator's own copy of the page.
    • This browser keeps the salt of every sealed claim it files. If the browser's storage is cleared, a filing made here can no longer be judged and its fee is lost.
    • The network follows redirects without saying so. Pin pages on a site that does not redirect.
    • A judgement that ends without a majority changes nothing and costs only the network fee, so a filing can be tried again inside its 30 minutes.
    • Withdrawals reach the wallet when their transaction is finalized.
